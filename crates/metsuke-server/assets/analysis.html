This server collects signed telemetry from the pools in the MusashiNet rewards program and keeps every submission exactly as it arrived. This page is how you get that archive onto a machine you can query. It is for whoever is analysing the data; the pool operators sending it start at the quickstart instead.

An archive object is one submission: a batch of metrics scrapes, or a batch of the node trace lines the program selects. Both are JSON Lines, compressed, and every line carries the pool and agent it came from. Nothing is aggregated and nothing is rewritten, so what you download is what a pool signed.

1. Get an account

The archive is not public. Reading it needs a developer account on this server, which is a username and a password held in the {{REALM}} realm, and the operators of this deployment are who issues one. Ask them, and put the password in a file of its own:

mkdir -p ~/.config/metsuke
$EDITOR ~/.config/metsuke/password
chmod 0600 ~/.config/metsuke/password

A file rather than a flag or a variable holding the secret itself: an argument is visible in the process table, and an environment variable reaches every child process and anything that may read /proc. The tool below takes the path and reads it itself.

2. Get the tool

metsuke-fetch is what pulls the archive down. It is one static binary with nothing to link against, the same as the agent:

{{fetch_install}}

On ARM it is metsuke-fetch-static-aarch64-linux. Either can be built rather than downloaded, with nix build {{flake}}#metsuke-fetch-static-$ARCH, and nix run {{flake}}#metsuke-fetch runs it without installing anything. {{fetch}} --help is the complete flag list; what follows is the part of it you need first.

3. Sync the archive

Point it at this server, say who you are, and name two paths: a cursor file and a directory to download into.

export METSUKE_FETCH_SERVER={{server_url}}
export METSUKE_FETCH_USER=<your account>
export METSUKE_FETCH_PASSWORD_FILE=~/.config/metsuke/password
export METSUKE_FETCH_TIMEOUT_MS=30000

{{fetch}} sync --state ~/.local/state/metsuke-fetch/cursor.json --into ~/archive

Each object lands under its own key, so the directory is safe to sync into repeatedly. The run prints what it did:

3 keys under v1/; 3 selected, 0 outside the selection, 0 this build cannot name
3 objects into ~/archive, 3145728 bytes; 1 cold-signed, 2 Leios-signed, 0 unattested, 0 not written

The cursor is what makes the next run a delta rather than a re-download: it records the last key seen, and a later run resumes past it. Deleting the file is the only way to start over, and the run after that downloads everything again, because nothing checks whether an object is already on disk.

Those three counts on the second line are how much of the archive proves itself. A cold-signed object was signed by a key that derives the pool it is filed under, so it stays checkable from the object alone, forever. A Leios-signed object had its signature checked here too, but which pool it belongs to is this server's word against a roster; its bytes are as authentic, and only the attribution rests on us. An unattested object came with nothing to check. Most of the archive is Leios-signed by design, and reading the archive has the flags that keep only what you are willing to trust.

Start with an unbounded sync as above. --from and --to exist and they bound by when this server received a submission, which is not when its rows were measured; an agent that spooled through an outage can put those days far apart. Slice by time in SQL, where the row's own timestamp is, rather than in the flags.

4. Read it

An object is a zstd stream whose first frame is skippable, so duckdb reads the downloaded tree where it landed with no unpacking step. It is not a useful select * though: a scrape holds its metrics as a nested list and a trace line holds its payload as a map, so both want flattening first. Two init files do that, and this server hands them out:

curl -O {{files_url}}analytics.sql
curl -O {{files_url}}archive.sql

analytics.sql is the one to start with. It defines the views a consumer actually groups over, coverage per agent, the block producer's scoreboard, the lifecycle of every endorsement block, and it answers most first questions without you writing a join:

duckdb -init analytics.sql
set variable archive = '/home/you/archive';

archive.sql is the same flattening with none of the views, as three tables over whatever directory you point it at. Load that one where your question is not one the views already answered. It globs recursively rather than assuming the archive's layout, and it keeps a row for every submission including the failed ones:

METSUKE_ARCHIVE=~/archive duckdb -init archive.sql archive.duckdb

Naming a database file as above makes the tables persist, so for later questions in another session open duckdb archive.duckdb and ask rather than re-reading every object. Both files carry their own instructions in their opening comments.

Further reading

Reading the archive is the complete account and the one to go to next. This page stops at getting you a first query; that document is why the read is not the obvious one, what makes an object provably a pool's, how the time bounds really behave, and the duckdb defaults that silently return NULL for a field they did not sample.

The agent, this server and the fetch tool are one repository, and its README is what each crate does. Everything the shape of this data rests on is written down as a decision on the record:

  • ADR 0005, why the archive keeps the raw signed bytes and nothing derived from them, which is what makes any of it checkable at all.
  • ADR 0001, the signature itself, and why it is detached.
  • ADR 0011, how a Leios key speaks for a pool, which is what the attribution of most of this archive rests on.
  • ADR 0004, the spool, which is why receipt time and observation time come apart.
  • CONTEXT.md, the vocabulary: what a Cold Key and a Leios Key are, and what a gap in an agent's sequence numbers does and does not tell you.
  • The other decisions, as the directory they sit in.
