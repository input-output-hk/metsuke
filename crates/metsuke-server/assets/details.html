Metsuke Details

What the agent sends, which key signs, and every config setting available is described on this page. The four steps to get running are the quickstart page, and nothing here is needed to follow them.

Your application code on chain

The rewards program emails you an application code when you apply. That code has to be in your pool registration transaction's metadata, under label {{METADATA_LABEL}}:

{{metadata}}

Only your cold key can sign a pool registration, so the two matching is what shows the application came from you. Until they match, this server refuses your submissions regardless of what key signs them. This is program registration rather than agent setup, so it is normally done before you reach the quickstart.

On NixOS

Add {{flake}} as a flake input and import its nixosModules.metsuke. That writes the configuration and the unit for you, including the two directives the journal source needs.

What leaves your machine

One submission is a plain JSON header, then your scrapes zstd compressed, one JSON object per line, with a detached Ed25519 signature over the whole byte sequence. The header rides in a zstd skippable frame, so zstd -d on a submission hands back the lines and nothing else. This is an example of the whole thing: two scrapes, the first cut down to two metrics where a real line carries every metric your node exposes, the second a scrape that failed.

{{envelope}}

One line per scrape, and its metrics are every metric your node exposes whose value JSON can hold. Those are the same metric lines curl prints when curling the metrics endpoint. Each entry carries the metric's name, its labels and its value as your node stated them, plus the declared_type its # TYPE line gave if it had one. The agent reads nothing else on your machine. It contributes two facts of its own: scraped_at, the time it scraped, and clock_offset_ms, the offset its own NTP query measured.

A scrape that failed is itself a signal, so the submission is sent either way: no metrics, and failure names what stopped it. Its reason is one of {{reasons}}, and its detail is the message the agent had: the port, the status, or the size limit it was configured with.

Every line names the pool and the machine that wrote it under metsuke, as pool_id and agent_id, the name you configure. One line read out of the archive on its own still says where it came from.

The header carries those same two, and four more: agent_version, the build that scraped; counter, which submission of yours this is; timestamp, when the submission was sealed; and schema_version, which shape its lines are.

Trace lines travel as their own submissions: the same header with schema_version 2, and then the lines selected by metsuke agent configuration, one per line, each containing the object your node wrote plus that same metsuke JSON key.

The signature travels beside the body in two headers: {{HEADER_VKEY}} and {{HEADER_SIGNATURE}}. Anything between your agent and this server has to pass both through unchanged, or the signature will not verify.

Which pool a submission is from is settled from those rather than taken on trust. A cold key hashes to your pool id, so this server derives it from the verification key in the first header. A Leios key hashes to nothing, so the submission names its pool in a third header, {{HEADER_POOL}}, and this server believes it only where its key roster lists that key for that pool.

Which key signs

Use your Leios key. Your node already forges and votes with it, so it is already on the machine the agent runs on and nothing new has to be put there. Signing telemetry is a poor reason to move a cold key onto a reporting host, which is what the other choice comes to.

The same goes if you report from your relays as well as your block producer. Every host that reports needs one of your keys on it, and a relay is the machine taking connections from strangers, so a cold key there is the worse version of the same mistake. Which host a submission came from is in it either way, under agent_id.

A cold key does work and this server accepts it, so it is an option if you have a reason to prefer it. If you use one it has to hash to the pool_id in your config, or the agent refuses to start.

The agent reads the bls.skey or pool.skey you already have.

The node's metrics endpoint

The published MusashiNet configuration already serves this on loopback, and the config the quickstart hands you already points there, so this section is a check and a repair kit rather than a step. The check:

curl -s {{metrics_url}}

If you receive metric lines back, there is nothing to do here. If nothing answers, your node's tracing has diverged from the published configuration, and this is the backend to add to its TraceOptions, bound to loopback so it is not reachable from anywhere else:

{{backend}}

If your node configuration has no TraceOptions at all, paste that as it stands. If it has one, merge into it rather than pasting over it. The "" key is your node's root entry, so keep every other key it has and add to its backends list.

Each backend replaces one of its own kind rather than joining it. If your root already names a PrometheusSimple or an Stdout backend, replace that one instead of keeping both. Get this wrong and metrics still work, the trace configuration below looks applied, and not one trace line is ever collected.

Stdout MachineFormat is what both trace sources of journald and pipe read, so it has to be in that list for either of them. Metrics alone do not need it.

Restart the node and run the check again.

What the node has to emit for trace lines

The metrics endpoint carries no per-event timestamps, so it cannot answer when an announcement arrived, when a block body and its closure were received, or when a quorum was reached. Those live in the node's trace stream, and the agent ships every field of the lines you select from it. It reads one field to decide, and it computes nothing from any of them.

The published MusashiNet configuration already emits all four, so again there is nothing to do unless your node's tracing has diverged from it. These are the namespaces, as keys to merge into your TraceOptions:

{{traces}}

Check before you add them. Your configuration may already set some of these, and merging replaces a key's whole entry, so these take the place of whatever severity or rate limit you had on those namespaces. It may also set rate limits on namespaces this snippet does not name; pasting over the object rather than merging into it would drop those too.

Each namespace carries its own severity, so your node's root threshold is left as you have it and nothing here depends on where you set it. There is no "" key in this snippet, so it cannot disturb the root entry the backend above touched. maxFrequency: 0 is not a typo, it means no rate limit, and leaving it out silently caps the stream.

Restart the node if you changed anything. What it emits is the same regardless of trace source; how the agent gets it is the choice below.

The pipe

In pipe mode the node runs as cardano-node run ... | {{binary}} --config {{config_path}}. The agent reads the node's stdout on its own stdin, holds no group at all, and writes every line through to its own stdout unchanged, so whatever read the node's output before still reads it.

It runs downstream of the node, so it needs no unit of its own. That makes this a change to the node's unit, and systemd has no pipelines, so the command is wrapped in a shell. This drop-in is the shape, and the empty ExecStart= is what clears the command the node's unit already had: node-pipe.conf, with config.pipe.toml beside it.

Wherever your node's command lives rather than in a unit, the pipeline goes there instead. A shell or a terminal writes it as it stands. Written around the command that starts a container it only works while that command stays attached, since a detached one prints an id rather than the node's output, so in a container the pipeline has to go inside, as the entrypoint.

The agent is a static binary, which is what makes that cheap: it needs no image of its own and nothing in the node's image has to match it. Mount it in beside the node. Against the MusashiNet node image, with the two pieces you supply marked:

docker run -d --name leios-relay --init \
  -p 3010:3010 \
  -v "$WORKING_DIR:/data" \
  -v "$WORKING_DIR/config:/app/config:ro" \
  -v /usr/local/bin/metsuke:/usr/local/bin/metsuke:ro \
  -v /etc/metsuke:/etc/metsuke:ro \
  -v metsuke-spool:/var/lib/metsuke \
  --entrypoint /bin/sh \
  ghcr.io/input-output-hk/ouroboros-leios/cardano-node-testnet:THE-TAG-THE-TESTNET-DOCS-PIN \
  -c '/app/run-node.sh | /usr/local/bin/metsuke \
        --config /etc/metsuke/config.toml \
        --signing-key /etc/metsuke/bls.skey'

/app/run-node.sh is that image's own launcher, which is what it runs when you do not override the entrypoint. On any other image, docker inspect prints the command to put there instead. The first three mounts and the port are the testnet documentation's own; the rest are the agent's, and only the tag is left to fill in.

Keep --init. A shell running a pipeline as PID 1 does not pass SIGTERM on to what it started, so without an init the runtime waits out the stop timeout and kills the node instead of letting it close its databases. That is a slow replay on the next start, and on a block producer it is the expensive kind of mistake.

The spool volume is what makes a restart cheap rather than lossy, and metrics_url needs no change: the agent is in the node's container network namespace, so the node's loopback is its own. That holds however the node binds its endpoint, since a wildcard bind includes loopback.

Write that metrics_url endpoint as an IP literal regardless of how the node binds it. Nothing resolves that host, so localhost is refused and it has to parse as a loopback address, meaning 127.0.0.1 or [::1].

The pipeline can also run on the host instead of inside the container, as docker logs -f --tail 0 <container> | {{binary}} --config {{config_path}}. That decouples the agent from the node's lifecycle and leaves the image alone, but it costs more than it looks. Reading the docker socket is root-equivalent on that host, whereas the entrypoint approach above needs no privilege at all. It also needs the node's metrics endpoint bound to a wildcard, and the MusashiNet image bakes in PrometheusSimple suffix 127.0.0.1 12798, so you would need to override its configuration to get one. The EXPOSE 12798 in that image does not help: a published port forwards to the container's interface, and nothing is listening there. And without --tail 0 a restart re-reads the whole log and sends it again.

None of that applies to the entrypoint above, which shares the node's container network namespace and so reaches the loopback the image already binds. The image ships Stdout MachineFormat in its backends either way, so the trace lines themselves need nothing.

The NixOS module only renders journald mode, not pipe mode.

The journal

In journald mode the agent reads the node's journal under its own unit. That costs it membership of the systemd-journal group, which reads every unit's journal on the host and is the one privilege it holds beyond scraping loopback. Two directives are the whole difference from the quickstart's unit, and journalctl needs both: metsuke-journald.service, with config.journald.toml beside it.

That config is the one place the agent cannot guess anything: neither your node's unit name nor where journalctl lives on your distribution.

Every setting

The quickstart ships the values that have to be set and leaves the rest at their defaults. config.example.toml is the annotated form of the same file, with every default written out. Its comments are pinned to the code, so a value there is a value the agent ships.

Reading further

The agent and this server are one repository, and its README is what metsuke is and which crate does what. Everything a decision here rests on is written down as an accepted decision rather than left in the code:

  • ADR 0007, why the agent scrapes loopback and nothing else, which is what puts it on your node host.
  • ADR 0010, the two trace sources and what each costs in privilege. The journal row's group is decided here.
  • ADR 0011, how a Leios key speaks for your pool, and what the key roster is.
  • ADR 0004, why the spool is the only place a scrape is kept, and what an unreachable server costs you.
  • ADR 0001, the signature over a submission, in the shape shown above.
  • ADR 0005, what the archive keeps of what you send, which is the bytes you signed and nothing derived from them.
  • Reading the archive, how your submissions are read back on the other side. Written for the developers processing this data rather than for you, which is what makes it the account of what your lines are used for.
  • The other decisions, as the directory they sit in.
