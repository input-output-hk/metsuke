metsuke

metsuke is a small agent you run beside cardano-node. It reads your node's Prometheus endpoint over loopback and sends this server a signed submission. It never opens your node socket, and it reads one key, the signing key you point it at.

Five steps below. What each file holds, and why, is on the details page.

1. Put your application code on chain

Your application to the rewards program carries a code. Put that same code in your pool registration transaction's metadata, under label {{METADATA_LABEL}}:

{{metadata}}

Only your cold key can sign a pool registration, so the two matching is what shows the application came from you. Until they match, this server refuses your submissions whatever key signs them.

2. Install the agent

On NixOS, add {{flake}} as a flake input and import its nixosModules.metsuke. That writes the configuration and the unit for you, and the rest of this page is a description of what it does.

Anywhere else, take the static build for your architecture:

nix build {{flake}}#metsuke-static-x86_64-linux
sudo install -m 0755 result/bin/metsuke {{binary}}

Use metsuke-static-aarch64-linux on ARM. There is no install script and no self-update.

3. Write the configuration

Save this as {{config_path}}, with your pool id, your node's Prometheus port, and this host in the upload URL.

{{config}}

Your node most likely serves Prometheus already, so use the port it is on. Check with:

curl -s {{metrics_url}}

If nothing answers there, the details page has the node configuration that opens it.

4. Install the key and the unit

Put your cold or Leios signing key at {{key_path}}, owned by root and moded 0400. The unit hands it over as a credential, so the service never reads that file itself and it stays unreadable to everything else. Which of the two keys to use is on the details page; either one works here.

{{unit}}
sudo systemctl daemon-reload
sudo systemctl enable --now metsuke

5. Check it

journalctl -u metsuke -f

The agent logs the endpoint it scrapes and the pool it reports for at startup, then one line per submission saying whether this server took it. The first submission is sent as soon as the agent starts, so you do not wait out a cadence to find out something is wrong. A refused submission logs this server's reason and the scrapes stay spooled, so nothing is lost while you fix it.

Trace lines, if you want them

Optional, and off unless you configure it. The metrics endpoint is a periodic snapshot, so it cannot say when an announcement arrived or when a quorum was reached. Those live in the node's trace stream. Turning it on takes one node configuration change, on the details page, and one of two sources:

  • the pipe, cardano-node run | metsuke. The agent reads the node's stdout and holds no group at all. It runs downstream of the node, so it needs no unit of its own.
  • the journal. The agent reads the node's journal under its own unit, which costs it the systemd-journal group, and that group reads every unit's journal on the host.

The pipe is the one that costs no privilege. The details page has the configuration and the unit for both.

Staying up to date

This server was built against agent {{CLIENT_VERSION}} and tells every agent that uploads to it which version that is. Yours logs a warning when it is older. To update, repeat step 2 and restart:

sudo systemctl restart metsuke

The spool is on disk, so queued scrapes survive the restart. Nothing is scraped while the agent is down.
