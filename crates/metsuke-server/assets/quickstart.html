Metsuke

{{logo}}

Metsuke is a small agent you run beside cardano-node on the Musashi network. It reads your node's Prometheus endpoint over loopback, collects the trace lines it has been configured for, and sends this server a signed submission. It never opens your node socket, and it reads only the signing key you point it at.

This assumes a node already running on the testnet, which the getting started guide is for, and a pool already in the rewards program, with your application code in your pool registration's metadata. Submissions are refused until it is. What that means.

Try it

Nothing is installed, and it all stops when you press Ctrl-C.

{{try_fetch}}
curl -O {{files_url}}config.pipe.toml

# Set your pool id, and a spool_path you can write
$EDITOR config.pipe.toml

cardano-node run ... | {{try_agent}} --config config.pipe.toml --signing-key bls.skey > /dev/null

That is the whole agent. It writes your node's output straight back out, and the redirect drops that copy: without it a node's trace stream buries what the agent has to say. What is left on your terminal is the agent's own. The first four lines arrive at once, and the scrape submission about ten seconds later, once the node has had time to bind its endpoint; the trace-line submission waits for the next upload, one hour by default:

{{journal}}

Drop the > /dev/null and your node's output comes back, interleaved with these lines. That pass-through is what the setups below depend on: whatever read your node's output before still reads it.

The config already points at this server, and its metrics URL is the port most nodes already serve Prometheus on. If your node is configured differently, that is the second line to change in the config file.

spool_path is the line a run from a shell usually has to change. It ships as the state directory the systemd setups below create, which a shell may not be able to write to by default, and the agent says so and stops rather than starting with nowhere to put a scrape.

How you'll run it for real

The setups, and what each costs. Everything below is the same four steps whichever row you take; only the filenames change.

The first row is what most pools want: the agent restarts without touching your node, and the group, which reads every unit's journal on the host, is the cost. The second gives up nothing in privilege but ties the agent's lifecycle to your node's, so restarting the agent restarts your node.

Both take a node that already runs as a systemd unit, the first also logging to the journal, which is where its trace lines are read from. cardano-node.service is an example to adapt where yours has no unit yet. It serves either row: the journald setup reads the journal it writes to, and the drop-in setup replaces the command it runs.

The last two are fallbacks rather than places to stay. Metrics only collects no trace lines, which the program wants, and is where to drop back to if collection is giving you trouble. A shell is the try-it above: nothing starts it at boot and nothing restarts it, so it is primarily for quick debugging.

1. Install the agent

{{install}}

One static binary, nothing to link against. On ARM it is metsuke-static-aarch64-linux. Either can be built rather than downloaded, with nix build {{flake}}#metsuke-static-$ARCH. There is no install script and no self-update. On NixOS, import the module instead and skip the rest of this page.

2. Configure it

Take the config your setup names in the table above, set your pool id, and put your signing key where the agent will look for it:

# Both the config and signing-key files go here, and nothing has made this
# directory yet
sudo mkdir -p {{config_dir}}

# Download one config file, and only one, from the preferred setup above

# Its own unit
sudo curl -o {{config_path}} {{files_url}}config.journald.toml

# Your node's unit, A container, or A shell
sudo curl -o {{config_path}} {{files_url}}config.pipe.toml

# Metrics only
sudo curl -o {{config_path}} {{files_url}}config.minimal.toml

# Set your pool id, and check the metrics URL. Two setups have more to set:
#   Its own unit  your node's unit, and journalctl's absolute path
#   A shell       a spool_path you can write
sudo $EDITOR {{config_path}}

# Install your signing key, bls.skey or pool.skey, readable by root alone
sudo install -m 0400 -o root -g root bls.skey {{key_path}}

The journald config names two things the agent cannot guess: your node's unit, and where journalctl lives on your distribution. They fail differently. A journalctl that is not at the path you gave stops the agent at startup and says so. A unit name that matches nothing does not: journalctl follows it and prints nothing, so the agent starts, ships its scrapes, and never ships a trace line.

agent_id is what a submission calls the machine it came from, and it needs no setting: unset, it is that host's hostname, which the startup line prints. Set it where the hostname is not the name you want, and in a container, where the hostname is the runtime's rather than yours.

Those permissions are for the three systemd setups, where the unit hands the key over as a credential and the service never reads the file itself. If you took A container or A shell, you point --signing-key at your own copy instead, and it needs to be readable by whoever runs the agent.

Both your Leios key and your cold key work; use your Leios key. Why.

There is nothing to configure for the trace lines themselves. The config you just took already selects the traces the program asks for, and the published MusashiNet node configuration already emits them. If you have changed your node's tracing, the details page offers further guidance.

3. Run it

Three branches from here, one per setup. If you took Its own unit or Metrics only, the agent runs under a unit of its own, and you download one of the two:

# Its own unit
sudo curl -o /etc/systemd/system/metsuke.service {{files_url}}metsuke-journald.service

# Metrics only
sudo curl -o /etc/systemd/system/metsuke.service {{files_url}}metsuke.service

# Start it now, and on every boot
sudo systemctl daemon-reload
sudo systemctl enable --now metsuke

If you took Your node's unit, the agent gets no unit of its own. A drop-in replaces the command your node's unit already runs with that same command piped through the agent. Why it is a drop-in.

# The directory is yours to make. The zzzz- name sorts the drop-in last, so
# nothing host-wide can clear its credential after it
sudo mkdir -p /etc/systemd/system/<your-node>.service.d
sudo curl -o /etc/systemd/system/<your-node>.service.d/zzzz-metsuke.conf {{files_url}}node-pipe.conf

# Replace YOUR-NODE-COMMAND with what your node already runs, which
# systemctl cat <your-node>.service prints
sudo $EDITOR /etc/systemd/system/<your-node>.service.d/zzzz-metsuke.conf

# Restarting the node is what starts the agent
sudo systemctl daemon-reload
sudo systemctl restart <your-node>

If you took A container or A shell, nothing above applies and nothing starts the agent for you: the pipeline goes in your container's entrypoint, which the details page shows whole against the MusashiNet node image, or a shell runs the try-it command at the top of this page.

4. Check it

Where the agent's own lines come out depends on your setup:

# Its own unit, or Metrics only
journalctl -u metsuke -f

# Your node's unit: the agent runs inside it, so its lines are the node's
journalctl -u <your-node> -f

# A container
docker logs -f <container>

# A shell: they are already on your terminal

Whichever command you ran, expect the same lines the try-it printed above, though not all at once. The first submission goes out on the first scrape rather than on a cadence, so the startup lines and the scrape one appear within seconds of each other and you do not wait out an interval to find out something is wrong. Trace lines have not accumulated by then, so theirs goes out on the next upload, one hour by default.

A refused submission logs this server's reason in place of one of those accepted lines, and the scrapes stay spooled, so nothing is lost while you fix it.

If you took Its own unit or Metrics only, a failure naming cannot read signing key under /run/credentials is usually the unit's credential being cleared rather than a permission problem. systemctl cat metsuke prints the unit and every drop-in that applies to it, including the host-wide ones under /usr/lib/systemd/system/service.d/ that the LXC and LXD images ship. A bare LoadCredential= in one of those resets the list after your unit's own line. Restore it in a drop-in that sorts after theirs.

sudo mkdir -p /etc/systemd/system/metsuke.service.d
sudo tee /etc/systemd/system/metsuke.service.d/zzzz-credential.conf >/dev/null <<'EOF'
[Service]
LoadCredential=signing-key:/etc/metsuke/signing-key
EOF

sudo systemctl daemon-reload
sudo systemctl restart metsuke

Your node's unit is already out of this: the drop-in you installed is named to sort after anything host-wide, which is what the zzzz- is for.

Staying up to date

This server was built against agent {{CLIENT_VERSION}} and tells every agent that uploads to it which version that is. The agent logs a warning when it is older. To update, repeat step 1, then restart whatever runs it:

# Its own unit, or Metrics only
sudo systemctl restart metsuke

# Your node's unit: the agent restarts with the node
sudo systemctl restart <your-node>

# A container
docker restart <container>

# A shell: run the try-it command again

The spool is on disk, so queued scrapes survive the restart. Nothing is scraped while the agent is down.
