metsuke

metsuke is a small agent you run beside cardano-node. It reads your node's Prometheus endpoint over loopback, collects the trace lines it has been configured for, and sends this server a signed submission. It never opens your node socket, and it reads only the signing key you point it at.

This assumes your pool is already in the rewards program, with your application code in your pool registration's metadata. Submissions are refused until it is. What that means.

Try it

Nothing is installed, and it all stops when you press Ctrl-C.

{{try_fetch}}
curl -O {{files_url}}config.pipe.toml

# Update your pool id
$EDITOR config.pipe.toml

cardano-node run ... | {{try_agent}} --config config.pipe.toml --signing-key bls.skey

That is the whole agent. Your node's output passes through it unchanged. You should see:

{{journal}}

The config already points at this server, and its metrics URL is the port most nodes already serve Prometheus on. If yours is elsewhere, that is the second line to change in the config file.

The first row is what most pools want: the agent restarts without touching your node, and the group is the cost. The second gives up nothing in privilege but ties the agent's lifecycle to your node's, so restarting the agent restarts your node.

The last two are fallbacks rather than places to stay. Metrics only collects no trace lines, which the program wants, and is where to drop back to if collection is giving you trouble. A shell is the try-it above: nothing starts it at boot and nothing restarts it, so it is primarily for quick debugging.

1. Install the agent

{{install}}

One static binary, nothing to link against. On ARM it is metsuke-static-aarch64-linux. Either can be built rather than downloaded, with nix build {{flake}}#metsuke-static-x86_64-linux. There is no install script and no self-update. On NixOS, import the module instead and skip the rest of this page.

2. Configure it

Take the config your row names, set your pool id, and put your signing key where the unit will look for it:

# Download the config your row names, the journald shape here
sudo curl -o {{config_path}} {{files_url}}config.journald.toml

# Update your pool id
sudo $EDITOR {{config_path}}

# Install your signing key, readable by root alone
sudo install -m 0400 -o root -g root bls.skey {{key_path}}

Those permissions are for the systemd shapes, where the unit hands the key over as a credential and the service never reads the file itself. From a shell or a container you point --signing-key at your own copy instead.

Both your Leios key and your cold key work; use your Leios key. Why.

Your node also has to emit the trace lines in the first place, which is one merge into its configuration. Skip that and metrics still arrive, but no trace lines ever will.

3. Run it

# Download the unit your row names, the journald shape here
sudo curl -o /etc/systemd/system/metsuke.service {{files_url}}metsuke-journald.service

# Start it now, and on every boot
sudo systemctl daemon-reload
sudo systemctl enable --now metsuke

If you took the pipe row instead, there is no unit of its own: the drop-in goes on your node's unit, or the pipeline goes in your container's entrypoint.

4. Check it

journalctl -u metsuke -f

The same lines the try-it printed. The first submission is sent as soon as the agent starts, so you do not wait out a cadence to find out something is wrong. A refused submission logs this server's reason in place of the last line, and the scrapes stay spooled, so nothing is lost while you fix it.

Staying up to date

This server was built against agent {{CLIENT_VERSION}} and tells every agent that uploads to it which version that is. The agent logs a warning when it is older. To update, repeat step 1 and restart:

sudo systemctl restart metsuke

The spool is on disk, so queued scrapes survive the restart. Nothing is scraped while the agent is down.
