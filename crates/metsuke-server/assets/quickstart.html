Metsuke

Metsuke is a small agent you run beside cardano-node on the Musashi network. It reads your node's Prometheus endpoint over loopback, collects the trace lines it has been configured for, and sends this server a signed submission. It never opens your node socket, and it reads only the signing key you point it at.

This assumes a node already running on the testnet, which the getting started guide is for, and a pool already in the rewards program, with your application code in your pool registration's metadata. Submissions are refused until it is. What that means.

Try it

Nothing is installed, and it all stops when you press Ctrl-C.

{{try_fetch}}
curl -O {{files_url}}config.pipe.toml

# Set your pool id, and a spool_path you can write
$EDITOR config.pipe.toml

cardano-node run ... | {{try_agent}} --config config.pipe.toml --signing-key bls.skey > /dev/null

That is the whole agent. It writes your node's output straight back out, and the redirect drops that copy: without it a node's trace stream buries what the agent has to say. What is left on your terminal is the agent's own. The first four lines arrive at once, and the scrape submission about ten seconds later, once the node has had time to bind its endpoint; the trace-line submission waits for the next upload, one hour by default:

{{journal}}

Drop the > /dev/null and your node's output comes back, interleaved with these lines. That pass-through is what the shapes below depend on: whatever read your node's output before still reads it.

The config already points at this server, and its metrics URL is the port most nodes already serve Prometheus on. If your node is configured differently, that is the second line to change in the config file.

spool_path is the line a run from a shell usually has to change. It ships as the state directory the systemd shapes below create, which a shell may not be able to write to by default, and the agent says so and stops rather than starting with nowhere to put a scrape.

The first row is what most pools want: the agent restarts without touching your node, and the group is the cost. It takes a node that already runs as a systemd unit and logs to the journal; cardano-node.service is an example to adapt where yours has no unit yet. The second gives up nothing in privilege but ties the agent's lifecycle to your node's, so restarting the agent restarts your node.

The last two are fallbacks rather than places to stay. Metrics only collects no trace lines, which the program wants, and is where to drop back to if collection is giving you trouble. A shell is the try-it above: nothing starts it at boot and nothing restarts it, so it is primarily for quick debugging.

1. Install the agent

{{install}}

One static binary, nothing to link against. On ARM it is metsuke-static-aarch64-linux. Either can be built rather than downloaded, with nix build {{flake}}#metsuke-static-$ARCH. There is no install script and no self-update. On NixOS, import the module instead and skip the rest of this page.

2. Configure it

Take the config your selected row names from the shape table above, set your pool id, and put your signing key where the unit will look for it:

# Both files below go here, and nothing has made it yet
sudo mkdir -p {{config_dir}}

# Download the config your row names, the journald shape here
sudo curl -o {{config_path}} {{files_url}}config.journald.toml

# Set your pool id, your node's unit and where journalctl lives
sudo $EDITOR {{config_path}}

# Install your signing key, bls.skey or pool.skey, readable by root alone
sudo install -m 0400 -o root -g root bls.skey {{key_path}}

The journald config names two things the agent cannot guess: your node's unit, and where journalctl lives on your distribution. They fail differently. A journalctl that is not at the path you gave stops the agent at startup and says so. A unit name that matches nothing does not: journalctl follows it and prints nothing, so the agent starts, ships its scrapes, and never ships a trace line.

agent_id is what a submission calls the machine it came from, and it needs no setting: unset, it is that host's hostname, which the startup line prints. Set it where the hostname is not the name you want, and in a container, where the hostname is the runtime's rather than yours.

Those permissions are for the systemd shapes, where the unit hands the key over as a credential and the service never reads the file itself. From a shell or a container you point --signing-key at your own copy instead.

Both your Leios key and your cold key work; use your Leios key. Why.

There is nothing to configure for the trace lines themselves. The config you just took already selects the traces the program asks for, and the published MusashiNet node configuration already emits them. If you have changed your node's tracing, the details page offers further guidance.

3. Run it

# Download the unit your row names, the journald shape here
sudo curl -o /etc/systemd/system/metsuke.service {{files_url}}metsuke-journald.service

# Start it now, and on every boot
sudo systemctl daemon-reload
sudo systemctl enable --now metsuke

If you took the pipe row instead, there is no unit of its own: the drop-in goes on your node's unit, or the pipeline goes in your container's entrypoint.

4. Check it

journalctl -u metsuke -f

The same lines the try-it printed, though not all at once. The first submission goes out on the first scrape rather than on a cadence, so the startup lines and the scrape one appear within seconds of each other and you do not wait out an interval to find out something is wrong. Trace lines have not accumulated by then, so theirs goes out on the next upload, one hour by default.

A refused submission logs this server's reason in place of one of those accepted lines, and the scrapes stay spooled, so nothing is lost while you fix it.

A failure naming cannot read signing key under /run/credentials is usually the unit's credential being cleared rather than a permission problem. systemctl show metsuke -p LoadCredential should name your key; an empty value means a host-wide drop-in reset it, as the LXC and LXD images do. Restore it in a drop-in that sorts after theirs.

sudo mkdir -p /etc/systemd/system/metsuke.service.d
sudo tee /etc/systemd/system/metsuke.service.d/zzzz-credential.conf >/dev/null <<'EOF'
[Service]
LoadCredential=signing-key:/etc/metsuke/signing-key
EOF

sudo systemctl daemon-reload
sudo systemctl restart metsuke

Staying up to date

This server was built against agent {{CLIENT_VERSION}} and tells every agent that uploads to it which version that is. The agent logs a warning when it is older. To update, repeat step 1 and restart:

sudo systemctl restart metsuke

The spool is on disk, so queued scrapes survive the restart. Nothing is scraped while the agent is down.
