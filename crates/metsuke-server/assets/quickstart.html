metsuke

metsuke is a small agent you run beside cardano-node. It reads your node's Prometheus endpoint over loopback, collects the trace lines you select, and sends this server a signed submission. It never opens your node socket, and it reads one key, the signing key you point it at.

This assumes your pool is already in the rewards program, with your application code in your pool registration's metadata. Submissions are refused until it is, whatever key signs them. What that means.

Try it

Four commands, one of them yours. Nothing is installed, and it all stops when you press Ctrl-C.

nix build {{flake}}#metsuke-static-x86_64-linux
curl -O {{files_url}}config.pipe.toml
$EDITOR config.pipe.toml                     # one line: your pool id

cardano-node run ... | ./result/bin/metsuke --config config.pipe.toml --signing-key pool.skey

That is the whole agent. Your node's output passes through it unchanged, so whatever read that output before still does. You should see:

{{journal}}

The config already points at this server, and its metrics URL is the port most nodes already serve Prometheus on. If yours is elsewhere, that is the second line to change.

How you'll run it for real

Three shapes, and what each costs. Everything below is the same four steps whichever row you take; only the two filenames change.

The first row is what most pools want: the agent restarts without touching your node, and the group is the cost. The second gives up nothing in privilege but ties the agent's lifecycle to your node's, so restarting the agent restarts your node. The last row collects no trace lines and is where to fall back if collection is giving you trouble; the program wants them.

1. Install the agent

One static binary, no dependencies:

nix build {{flake}}#metsuke-static-x86_64-linux
sudo install -m 0755 result/bin/metsuke {{binary}}

Use metsuke-static-aarch64-linux on ARM. There is no install script and no self-update. On NixOS, import the module instead and skip the rest of this page.

2. Configure it

Take the config your row names, set your pool id, and put your signing key where the unit will look for it:

sudo curl -o {{config_path}} {{files_url}}config.journald.toml
sudo $EDITOR {{config_path}}                 # one line: your pool id
sudo install -m 0400 -o root -g root pool.skey {{key_path}}

The unit hands that key over as a credential, so the service never reads the file itself and it stays unreadable to everything else. Either your cold key or your Leios key works; which one to use is worth two minutes.

Your node also has to emit the trace lines in the first place, which is one merge into its configuration. Skip that and metrics still arrive, but no trace lines ever will.

3. Run it

sudo curl -o /etc/systemd/system/metsuke.service {{files_url}}metsuke-journald.service
sudo systemctl daemon-reload
sudo systemctl enable --now metsuke

If you took the pipe row instead, there is no unit of its own: the drop-in goes on your node's unit.

4. Check it

journalctl -u metsuke -f

The same lines the try-it printed. The first submission is sent as soon as the agent starts, so you do not wait out a cadence to find out something is wrong. A refused submission logs this server's reason in place of the last line, and the scrapes stay spooled, so nothing is lost while you fix it.

Staying up to date

This server was built against agent {{CLIENT_VERSION}} and tells every agent that uploads to it which version that is. Yours logs a warning when it is older. To update, repeat step 1 and restart:

sudo systemctl restart metsuke

The spool is on disk, so queued scrapes survive the restart. Nothing is scraped while the agent is down.
